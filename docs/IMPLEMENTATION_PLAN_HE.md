## תוצר היעד הראשון

מסלול עצמאי, מקומי וניתן לבדיקה:

`Markdown ב־Vault → טיוטת ידע → סקירה ואישור → embeddings ואינדקס פעיל → שאלת בישול → שליפה מאושרת → בדיקת מדיניות → תשובה עם הפניות לגרסאות המקור`

השירות יעבוד כאשר Obsidian סגור, ללא תלות באתר Cook Pilot. הוא יציע פעולות; הוא לא יפעיל מכשירי מטבח או יבצע פעולה פיזית.

## גבולות המהדורה הראשונה

- שירות Python/FastAPI, אחסון PostgreSQL עם pgvector, חוזי Pydantic ותיעוד OpenAPI.
- Vault מקומי של Markdown עם frontmatter, קליטה, סקירה, אישור, גרסאות ושליפה.
- מנוע שף טקסטואלי, ציטוטים ניתנים לבדיקה ומדיניות בטיחות וכשרות עצמאית.
- הערכה ראשונית של 15–20 תרחישים, בדיקות אוטומטיות ותיעוד תפעולי.
- מחוץ למהדורה: ממשק משתמש מלא, פריסה בענן, חיבור בפועל ל־Cook Pilot, תוסף Obsidian, קליטת ספרים שלמים, תמונה/קול והרחבת תשתית לסוכנים עצמאיים.

## ארכיטקטורה מוצעת

1. **API:** אימות, הרשאות, סכמות בקשה/תשובה, גרסאות ו־idempotency.
2. **Chef Engine:** בניית הקשר מגרסה מזוהה של החוקה, מצב הבישול והידע המאושר; יצירת החלטה מובנית.
3. **Knowledge Ingestion:** קריאת Markdown, אימות מטא־דאטה, יצירת הצעות ידע ותור סקירה.
4. **Knowledge Retrieval:** סינון לפי סטטוס וגרסה פעילה, חיפוש טקסטואלי/וקטורי ומיזוג תוצאות; reranking רק אם ההערכה מצדיקה זאת.
5. **Policy Engine:** בדיקות דטרמיניסטיות של אילוצים לפני יצירת הצעה ולפני החזרת פעולה. מודל השפה אינו מוסמך לעקוף חסימה.
6. **Evaluation:** תרחישים קבועים, רישום גרסאות והשוואת תוצאות.
7. **Adapters:** ספק מודל, embeddings, מערכת קבצים ותור עבודות מאחורי ממשקים הניתנים להחלפה.

התפקידים יתחילו כמודולים ופעולות workflow באותו שירות. אין הצדקה בשלב זה להקמת סוכנים עצמאיים או תשתית orchestration נוספת.

## שלב 3 — קליטה ידנית, סקירה ואישור אטומי

זהו הבסיס למסלול הראשון. קליטה מפורשת דרך API קודמת ל־watcher כדי לצמצם משתנים.

**משימות:**

- קליטת Markdown אחד מתוך תיקיית Vault מוגדרת; הגבלת גודל וקידוד ומניעת גישה מחוץ לתיקייה באמצעות נתיבים או symlinks.
- אימות frontmatter, מזהה מקור, רישיון ומזהים יציבים; אין הפעלה של תוכן Markdown כקוד.
- שמירת hash וגרסת מקור; יצירת יחידות ידע מוצעות עם סטטוס `pending_review`.
- חילוץ עקרונות, תנאים, חריגים, תצפיות ופעולה מומלצת כהצעות הניתנות לעריכה; סימון שדות חסרים במקום השלמת עובדות.
- איתור כפילויות מדויקות לפי hash ומזהה; הצעת דמיון/סתירה לסוקר בלי מיזוג או מחיקה אוטומטיים.
- API לאישור, דחייה ותיקון גרסה עם בדיקת revision כדי למנוע דריסת סקירה מקבילה.
- `idempotency_key`: חזרה על אותה בקשה עם אותו תוכן מחזירה אותה תוצאה; שימוש חוזר במפתח עם תוכן אחר נדחה.
- רישוי לא ידוע או לא מאושר אינו מאפשר הפעלת ידע.

**תכנון הפעלה:** `draft → pending_review → approved_pending_index → active`, ולצדם `rejected` ו־`superseded`. לאחר אישור הסוקר נוצרים embeddings. רק לאחר הצלחה של האינדוקס מתחלף מצביע הגרסה הפעילה בטרנזקציה. קריאת ספק חיצוני לא תחזיק טרנזקציית מסד פתוחה. כשל באינדוקס משאיר את הגרסה הפעילה הקודמת זמינה ומאפשר retry בטוח.

**שער קבלה:** יבוא חוזר אינו משכפל ידע; טיוטה אינה נשלפת; אישור ואינדוקס מוצלחים מפעילים גרסה ללא restart; כשל אינדוקס אינו מפעיל גרסה חלקית.

## שלב 4 — תשובת שף מבוססת ידע עם מדיניות מינימלית

**משימות:**

- שליפה רק מתוך גרסאות פעילות ומקורות מורשים; סינון זה נאכף בשכבת האחסון ולא רק ב־prompt.
- חיפוש משולב בעברית/אנגלית ובדיקת התאמה למצב הבישול, לאילוצים ולתנאי התחולה של יחידות הידע.
- בניית הקשר עם גבול ברור: החוקה היא מדיניות; מסמך מקור והודעת משתמש הם מידע ואינם הוראות לעקיפתה.
- חיבור לספק מודל דרך adapter; שמירת מזהי גרסת חוקה, prompt, מודל ואינדקס לכל החלטה.
- ציטוט לכל המלצה מהותית: מזהה מקור, גרסת מקור, מזהה יחידת ידע ומקטע תומך. אימות שרת שהציטוט אכן שייך לתוצאות שהותרו לשליפה.
- במקרה שאין תמיכה מספקת: שאלת הבהרה או תשובה מוגבלת עם ציון הפער, ללא המצאת מקור.
- כללי חובה ראשונים: ניגוד בשר/חלב בפרופיל האוסר זאת, מידע חסר על רכיב/תנאי בישול, ואיסור לטעון שנמדדה טמפרטורה או נצפה מזון ללא דיווח מתאים.
- בדיקת קלט ומדיניות לפני יצירת התשובה, ובדיקת הפעולה והתשובה לאחריה. פעולה חסומה תוחזר כלא־מותרת גם אם הטקסט שהמודל יצר מציע אותה; התשובה ללקוח תותאם כדי לא לכלול הוראות סותרות.

**שער קבלה — המסלול האנכי הראשון:** Markdown מקורי מורשה עובר קליטה ואישור; שאלת הבצל נענית עם הפניה לגרסה המאושרת; הגרסה הלא מאושרת אינה מצוטטת; פרופיל כשרות מתאים חוסם את הדוגמה הבשרית־חלבית. בדיקות אלו פועלות ללא Obsidian וללא ממשק משתמש.

## שלב 5 — סנכרון Vault וגרסאות מלא

**משימות:**

- watcher עם debounce וסריקה תקופתית משלימה; שמירת מצב סריקה לצורך התאוששות מאירועים שהוחמצו.
- שינוי קובץ יוצר revision חדש לסקירה, לא עדכון שקט של הידע הפעיל.
- שמירת זהות באמצעות מזהה יציב ב־frontmatter גם לאחר שינוי שם או מעבר תיקייה.
- מחיקה יוצרת הצעת הסרה לסקירה. עד לאישור, הגרסה הפעילה נשמרת בהתאם למפרט.
- rollback מצביע לגרסה קודמת עם היסטוריה, בלי מחיקת audit trail.
- גרסת אינדקס נפרדת לכל מודל embeddings; החלפת מודל/ממד דורשת reindex לצד האינדקס הפעיל והחלפה אטומית לאחר בדיקה.
- שינויים מ־Obsidian פועלים גם כאשר היישום עצמו סגור.

**שער קבלה:** שינוי, העברה, שמירה חוזרת ומחיקה אינם משכפלים או מוחקים בשקט ידע פעיל; סריקה מחזירה עקביות לאחר watcher שהפסיק לעבוד; rollback ניתן להוכחה בבדיקה.

## שלב 6 — הרחבת מדיניות וחבילת הערכה

**משימות:**

- הרחבת כללי הכשרות והבטיחות על בסיס הדרישות והמקורות שאושרו בשלב 1, עם מקרי גבול ושלילה.
- הכנת 15–20 תרחישים בעברית, ובהמשך מדגם באנגלית: בצל שמשחים מוקדם, רכיב חסר, יחידות מלאי, תנאים לא ידועים, מקור סותר, מקור לא מאושר, ציטוט מזויף, הוראה עוינת במקור, חוסר דיווח טמפרטורה וכשל ספק.
- לכל תרחיש: קלט, מזהי ידע נדרשים/אסורים, סוג החלטה צפוי, אילוצים מחייבים ומחוון איכות תשובה.
- מדידת retrieval בנפרד מיצירת תשובה: החזרת יחידות רלוונטיות, יחידות אסורות, התאמת ציטוטים והימנעות כשאין ראיות.
- שילוב בדיקות דטרמיניסטיות עם בדיקת אדם לאיכות ההסבר. שופט מבוסס מודל, אם יתווסף, אינו מחליף שערי בטיחות או הרשאות.
- דוח המשווה גרסאות מודל, חוקה, prompt ואינדקס; ספי איכות לשפה ולהסבר ייקבעו על בסיס baseline, לא מספר שרירותי מראש.

**שער קבלה:** אפס חשיפות של ידע לא מאושר ואפס מעקפים בתרחישי המדיניות המחייבים בחבילת הבדיקה. מעבר חבילה אינו הוכחה לבטיחות כללית מחוץ לכיסוי שנבדק.

## שלב 7 — תפעול, גיבוי וחוזה חיבור עתידי

**משימות:**

- README מלא, דוגמאות API, הוראות התקנה, תצורת ספקים ופתרון תקלות.
- גיבוי מסד הנתונים וה־Vault, תיעוד גרסאות ועבודת שחזור הנבדקת בפועל.
- ניטור כשלים בקליטה/אינדוקס/ספק והפרדת לוגים טכניים מתוכן אישי.
- בדיקת עלויות וזמני תגובה במדגם המתועד; הגדרת timeouts ומגבלות בקשה על בסיס התוצאות.
- תיעוד חוזה חיבור עתידי של Cook Pilot ל־`/v1/chef/respond`; ללא שינוי באתר הקיים במסגרת מהדורה זו.
- תכנון ענן עתידי עם sync agent מאומת או Git פרטי, ללא חשיפת תיקיית Vault לאינטרנט. חיבור ופריסה בפועל הם עבודה נפרדת.

**שער קבלה:** אפשר לשחזר סביבה חדשה מגיבוי ולהפיק תשובה עם אותן הפניות לגרסאות הידע; ההתקנה אינה תלויה ב־Obsidian או ב־Cook Pilot.

## מודל נתונים מוצע

| ישות | תוכן מרכזי |

| `ReviewDecision` | הסוקר, revision שנבדק, אישור/דחייה/הסרה ונימוק |
| `IndexRevision` / `Embedding` | גרסת ידע, מודל וממד embedding, מצב בנייה והפעלה |

| `EvaluationRun` | תרחישים, תצורה, תוצאות, כיסוי וכשלים |

## API מתוכנן

## אסטרטגיית בדיקות

- **Unit:** frontmatter, מזהים/hash, יחידות ידע, רישוי, תנאי מדיניות ואימות ציטוטים.
- **Integration:** PostgreSQL/pgvector אמיתי, migrations, אישור/אינדוקס, כשל באמצע הפעלה, הרשאות ועדכונים מתחרים.
- **Workflow:** יבוא חוזר, שינוי קובץ, מחיקה מוצעת, rollback ואירוע watcher שהוחמץ.
- **Evaluation:** שאלות בישול, סתירות, מידע חסר, ניסיונות עקיפה והפרדת מקור/דיווח/הסקה.
- בדיקות רגילות משתמשות בספק מודל ו־embeddings מדומים. בדיקות ספק חי הן ריצה נפרדת ומפורשת, עם תקציב ותיעוד; CI רגיל אינו תלוי בהן.
- בהתאם להעדפה הקודמת, במימוש עתידי ניתן לחלק כל מחזור לשבע משימות מימוש לפני הפעלת הבדיקות. אין לדחות את כל הבדיקות עד סוף שבעת שלבי הפרויקט: כל מסלול קטן נבדק לפני שמרחיבים אותו.

## הגדרת השלמה

המהדורה תיחשב שלמה כאשר כל דרישת חובה ניתנת למעקב מהמסמך לקוד ולראיית בדיקה; כל המלצה מהותית חוזרת למקור מורשה ולגרסה מאושרת; ידע לא מאושר אינו נחשף; סתירות וחוסר מידע נשמרים גלויים; שינויי Vault אינם פוגעים בשקט בידע הפעיל; השירות ניתן להתקנה ולשחזור ללא האתר הקיים.

תוכנית זו אינה מעידה שהשירות, הכללים, הבדיקות או חיבורי הספק כבר מומשו.
